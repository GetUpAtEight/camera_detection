# 代码审查报告 · 摄像头篡改检测（低频巡检）

> 审查范围：`algo/`（Python 算法层）、`backend/`（SpringBoot 透传层）、`frontend/`（Vue3 前端）、`deploy/`（部署脚本）、启动脚本与测试。
> 审查性质：**只读**，未修改任何代码。
> 审查日期：2026-10-27

---

## 一、总体评价

这是一个**结构清晰、设计克制、可解释性强**的工程。核心亮点在于：

1. **单一算法实现**：所有判定只在 Python 算法层实现一份，SpringBoot 后端只做透传与校验，避免了「双语言逻辑漂移」这一长期维护隐患。
2. **状态落盘设计合理**：低频采样（1 小时一次）意味着进程内状态必然过期，因此机位基线、参照物、模板、审计全部按 `cameraId` 落盘（JSON + NPZ），重启不丢。
3. **防御式算法思维**：代码注释和测试里反复出现「先排除陷阱再定罪」的工程判断（如压缩流静止画面不能首次就判冻结、纯色画面 ORB 伪匹配不能拿来配准、光度对齐不能把遮挡也归一化掉），说明作者对误报路径有清醒认识。
4. **测试覆盖扎实**：`test_sparse.py` 覆盖 27 组场景、59 项断言，且全部是确定性合成画面，可复现。

**总体评分：4.5 / 5**（作为 demo / 验证级项目已相当完整；距离生产还有若干工程化事项，见下文）。

## 二、架构概览

```
浏览器（Vue3 + Element Plus + ECharts）
        │  REST / multipart
        ▼
SpringBoot 3（透传 + 校验，无业务状态、无数据库）
        │  HTTP（JSON + multipart）
        ▼
Python FastAPI（低频巡检算法层，纯 CPU）
        │  机位基线按 cameraId 落盘（JSON + NPZ）
        ▼
algo/data/sparse/
```

三层信号模型是本系统的骨架：

| 层 | 时间尺度 | 回答 |
|---|---|---|
| L2 单帧 | 任意一帧 | 这一帧好不好（失焦/遮挡/画质） |
| L1 微时序 | 一次抽样内 K 帧 | 这几秒画面动没动、是不是真摄像头 |
| L0 跨采样点 | 相邻抽样间隔 | 跟本机位历史比有没有变 |

核心是「稳定性分解」：`dHist（历史偏离） × dBurst（微时序动态）` 构成 4 格矩阵，把**持续篡改**与**有人路过的瞬时事件**分开——这是低频场景下最有价值的设计。

## 三、各模块审查结论

### 3.1 算法层 `algo/`（核心）

**`server.py`（FastAPI 入口）**
- ✅ 启动即设置 `OMP/MKL/OPENBLAS_NUM_THREADS=1`，避免 CPU 过度订阅；单 worker 设计有明确理由（`CameraStore` 进程内持锁）。
- ✅ 全局异常兜底不泄露内部细节（只返回异常类型名 + 提示看日志）。
- ✅ CORS 白名单只放行本机开发端口。
- ⚠️ **无鉴权**：`/sparse/*` 所有接口（含删除机位、清空基线）无需任何认证。README 已明确标注「部署到公网前必须自行加」，但这仍是最大的安全缺口。
- ⚠️ `_read_upload` 逐帧解码，12 帧大图时 CPU 峰值会叠加，但低频场景可接受。

**`engine.py`（判定核心，约 1150 行）**
- ✅ 判决优先级清晰（P-1 样本可用性 → P0 冻结 → P5 正在转动 → 稳定性分解 → P1~P4 类型投票），且每一支都写了 `reasons` 原因链，可解释性极强。
- ✅ 冻结判据 D1/D3 的「首次抽样不定罪」处理正确，避免了压缩流静止画面误报。
- ✅ 遮挡 vs 失焦的区分用「全局对比度崩塌」这个信号，抓住了纸面/手掌遮挡「熵只掉 20% 但灰度标准差掉到几分之一」的本质。
- ⚠️ **`_decide` 方法过长**（约 250 行），分支嵌套较深；虽注释充分，但后续维护成本会随判据增加而上升，建议按「冻结 / 转动 / 持续性 / 类型投票」拆成更小的纯函数。
- ⚠️ 大量硬编码阈值散落在 `_decide` / `_classify_persistent` 里（如 `0.35`、`0.5`、`15.0`、`0.0035`、`0.0035` 等），未纳入 `DEFAULT_PARAMS`，不利于调参和解释。

**`metrics.py`（底层指标，约 1000 行）**
- ✅ 指标确定性强、便宜、可解释（detail 给原始值而非 0~1 分数）。
- ✅ `match_landmark` 的「无纹理窗口 TM_CCOEFF_NORMED 虚高分」防呆（`energyRatio < 0.30` 判 flatMatch）非常关键，直接堵住了「全遮挡被判成匹配极好」的致命误报。
- ✅ 子块投票、多尺度粗搜 + 精修、峰值唯一性判据设计完整。
- ⚠️ `_ORB` 是模块级全局单例（`cv2.ORB_create`），在单 worker 下安全，但若未来改多 worker/多线程需注意线程安全。
- ⚠️ `orb_translation` / `orb_affine` 的 `estimateAffinePartial2D` 未设随机种子，RANSAC 结果在边界场景下可能非确定性（对同一次调用的稳定性影响极小，但严格可复现性会打折）。

**`store.py`（持久化）**
- ✅ JSON 写用临时文件 + `os.replace` 原子替换，避免写一半损坏。
- ✅ `_safe_id` 对 cameraId 做白名单清洗（只保留字母数字与 `-_`），有效防止路径穿越。
- ✅ MAD 下限（`MAD_FLOOR=2.0`）封底，避免「过度稳定基线」把 z 放大失真。
- ⚠️ 单文件 `cameras.json` 索引 + 每个机位独立 JSON/NPZ，扩展性受限于单机单目录；机位数上千后 `list_cameras` 全量读索引、`save` 每次全量重写该机位 NPZ 会成为瓶颈（当前 demo 规模无碍）。
- ⚠️ `save` 时若 `arrays` 为空，NPZ 不会重建，旧 NPZ 文件可能残留（`delete` 已处理，但 `reset` 后旧 NPZ 未被清理，只是不再被读）。

**`media.py`**
- ✅ 视频抽帧逻辑严谨（seek 容错、全局帧号取模保证整段/区间一致、绝对时间戳对齐标注）。
- ✅ `expected_sampled_frames` 精确计数避免进度条虚高。
- ⚠️ 多数函数未被算法层实际调用（`probe_video`、`read_frame_at`、`iter_frames` 等），疑似从实时检测方案遗留，属死代码，可考虑清理或明确标注保留用途。

### 3.2 后端 `backend/`（SpringBoot）

- ✅ 分层清晰：Controller → Service → AlgoGatewayService，职责单一。
- ✅ `GlobalExceptionHandler` 兜底不回显异常原文，4xx 透出算法层 detail、5xx 只回状态码，安全边界处理得当。
- ✅ `AlgoGatewayService.mapHttpError` 正确解析 FastAPI 的 `{"detail": ...}` 结构。
- ✅ RestTemplate 关闭请求体缓冲（`setBufferRequestBody(false)`），大图流式写出。
- ✅ 临时文件在 `finally` 中清理。
- ⚠️ **路径拼接未做 URL 编码**：`get("/sparse/state/" + cameraId)` 等直接字符串拼接。虽然算法层有 `_safe_id` 白名单清洗兜底，但 `cameraId` 若含 `/`、`?`、`#` 等字符会导致路径错乱或请求注入，建议在网关层对 cameraId 做 `UriComponentsBuilder` 编码。
- ⚠️ `sparseRemoveTemplate` 的 `actor` 直接拼进 query 字符串，未编码。
- ⚠️ 无鉴权、无多租户隔离（与算法层一致，README 已标注）。

### 3.3 前端 `frontend/`（Vue3 + TS）

- ✅ 类型定义完整（`SparseResult`、`SparseMeta` 等），API 层用 axios 拦截器统一解包 `{code, message, data}`。
- ✅ `SparseView.vue` 交互完整：标定框选、忽略区、模板库、一键演示、24 槽画廊、4 格矩阵 ECharts。
- ✅ 一键演示自包含（无底图时回退内置样图），零准备可跑。
- ⚠️ `SparseView.vue` 是**单文件 2000 行的巨型组件**，模板 + 逻辑 + 样式 + 采样来源 + 标定对话框全部塞在一个 `.vue` 里，可读性与维护性明显下降。建议至少把「参照物标定对话框」「矩阵图渲染」「采样来源抓帧」拆成独立子组件/composable。
- ⚠️ 大量 `any` 类型（`result.layers?.L1?.[...]`、`stateData = ref<any>`），TS 的强类型优势未充分发挥。
- ⚠️ `http` 实例 `timeout: 0`（永不超时），虽然单次 sample 用 `timeout: 120000` 覆盖，但其它 GET 接口无超时保护，算法层挂起时会一直等待。
- ⚠️ 前端「采样时间推进」直接构造 `tsMs` 传给后端，存在客户端时钟被篡改/漂移的风险（demo 可接受，生产应由服务端定时间）。

### 3.4 部署 `deploy/` 与启动脚本

- ✅ `remote.py` 设计克制：一条 SSH 连接复用（规避服务器认证限流）、只读写 `ctd_service` 目录、密钥优先、`.env.local` 不入库。
- ✅ 桥接脚本用 `os.read(0, 65536)` 而非 buffered `read(n)`，规避了「请求卡在建连阶段」的经典坑。
- ✅ 远端停旧进程按 `cwd` + `cmdline` 双重判定，只动本服务，不误杀同目录他人进程。
- ⚠️ `remote.py` 使用 `setsid nohup` 后台启动远端服务，若隧道中断，远端服务仍在跑（watchdog 会拉起），但**本地端口转发的并发模型是每连接一线程 + 每请求新建一条 SSH session 通道**，高并发下会有开销；对低频巡检场景影响有限。
- ⚠️ `start_all.sh` 中 pip 用 `https://pypi.org/simple`（非镜像），国内环境可能慢（README 已提示换镜像，但脚本内未用镜像）。

## 六、亮点总结（值得保留的设计）

1. **「稳定性分解」4 格矩阵**——用「历史偏离 × 微时序动态」把持续篡改与瞬时事件分开，是低频采样场景的解题关键。
2. **参照物标定 + 相似变换拟合**——用「多个静止结构符合同一个刚体变换」替代「全图相位相关」，从根本上解决了树影/行人/车辆导致的移位误报。
3. **模板库 + 人机共驾 + 三重闸**（质量闸、去重闸、审计）——把「误报反馈加模板」这个高风险操作管住了，防止把攻击学成正常。
4. **光度对齐 + 忽略区**——分别压制「天气变暗变灰」和「桌面东西被挪」两类高频误报。
5. **冻结判据的物理基础**（独立传感器噪声 + 跨采样点 bit-exact），并正确处理「首次抽样不定罪」「压缩流静止画面」两个陷阱。
6. **后端无数据库、无状态**，攻击面小，运维负担低，架构上「算法单一实现 + 状态在算法层落盘」的取舍正确。

## 七、结论

该项目作为**低频巡检摄像头篡改检测的 demo / 验证级实现**，质量明显高于一般原型：架构取舍合理、算法防御性强、测试覆盖扎实、文档完整（README / SPARSE / API / DEPLOY 四份 + 研究文档）。

距离生产主要差在三点：**鉴权与多租户**、**后端/前端测试**、**前端巨型组件的可维护性**。若按第五节高优先级清单补齐，即可作为可部署的内部巡检工具上线。
